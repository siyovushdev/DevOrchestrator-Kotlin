# DevOrchestrator — Техническое задание v0.1

**Статус:** DRAFT · **Этап:** M0 · **Дата черновика:** 2026-10-17.  
**Утверждённые части:** ADR-001 (Project Registry) и ADR-002 (Lifecycle/Recovery, R-01–R-06). PRD в целом остаётся DRAFT до финального согласования M0.

## 1. Зачем создаём

Система должна уменьшить ручную координацию ИИ-разработки: пользователь ставит задачу в ChatGPT или GitHub; DevOrchestrator сам находит подходящий разрешённый проект, запускает Coding, проверки, независимый Review и создаёт Draft PR. Пользователь следит за результатами и принимает решение о Merge. В дальнейшем — наблюдает и управляет с Android.

**Главный критерий пользы:** задача завершается полезным Draft PR, а не сотнями тестов самого оркестратора и ручной передачей промптов.

## 2. Границы MVP

- Одна управляющая машина Linux WORK; один основной Kotlin/JVM-сервис и одно авторитетное состояние.
- GitHub — источник задач и место публикации Draft PR.
- Первый реальный Coding-адаптер — Codex CLI. Ядро **не привязано** к Codex: другие Coding/Review/Planner/Chief агенты подключаются через единый контракт и каталог профилей; независимый Review работает отдельной сессией/контекстом.
- Автоматическое исполнение допускается **только для явно зарегистрированных и разрешённых PERSONAL проектов** по ADR-001.
- Для WORK/1МТ — отдельное ручное Owner GO на запуск и публикацию.
- Owner всегда принимает Merge самостоятельно. По утверждённому ADR-002/R-04 Chief AI не обязателен до Draft PR в PERSONAL MVP; дополнительные gates определяет проектная политика.

## 3. Роли

- **Owner**: регистрирует проекты, управляет политиками, видит состояние, останавливает или разрешает операции.
- **Orchestrator**: принимает задачи, управляет состояниями, процессами, доказательствами, публикацией и восстановлением.
- **Coding Agent**: изменяет код в изолированной среде и сообщает конкретный результат.
- **Review Agent**: получает независимый снимок diff и проверяет изменения отдельно от Coding-сессии.
- **Agent Selector / Planner**: выбирает разрешённые agent profiles для задачи вручную, по правилам либо через AI Routing; не имеет права менять project policy, секреты или доступы.
- **GitHub**: источник внешних идентификаторов задач и PR, не источник полномочий.

## 4. Функциональные требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Project Registry и политики (ADR-001) | Чужая/неизвестная Issue не запускается, разрешённая определяется по доверенному repo ID |
| FR-02 | GitHub intake | Новая разрешённая Issue появляется в SQLite ровно как одна логическая задача |
| FR-03 | Durable workflow | Фаза, попытка, события и результаты восстанавливаются после restart без повторного запуска |
| FR-04 | Coding | Система сама запускает реальный Codex и сохраняет статус, логи и diff |
| FR-05 | Verification | PASS, FAIL, NOT_RUN не смешиваются; команда/exit-code/артефакты связаны с попыткой |
| FR-06 | Independent Review | Отдельная сессия проверяет зафиксированный diff, а не самоотчёт Coding |
| FR-07 | Correction loop | Не более установленного проектом лимита; каждый повтор имеет уникальный attempt ID |
| FR-08 | Draft PR | После условий политики публикуется только Draft PR с проверяемым head/base; Merge запрещён |
| FR-09 | Recovery | При сомнительном внешнем эффекте система проверяет GitHub/Git, а не повторяет запись вслепую |
| FR-10 | Owner control | Владелец может видеть BLOCKED/UNKNOWN и приостанавливать новые действия |
| FR-11 | Compact status | Для задачи видны фаза, агент, тесты, PR, блокер и один следующий шаг |
| FR-12 | Audit trail | Изменение политики, решения и внешние эффекты имеют автора/время/идентификатор |
| FR-13 | Расширяемый Agent Catalog | Новый совместимый агент (например, Cursor/Claude/Gemini/Kimi/OpenCode) добавляется через adapter + конфигурацию без переделки Workflow Engine; неподключённый adapter не считается доступным |
| FR-14 | Динамические роли и профили | Owner задаёт или изменяет профили `Coding`, `Review`, `Planner`, `Chief` (необязательный): agent, provider, model, reasoning effort, capabilities, sandbox, limits; назначение по проекту/задаче |
| FR-15 | Ручной или автоматический выбор | Режим `MANUAL`/ `AUTO_RULES`/ `AUTO_AI`: система может сама выбрать разрешённого агента/модель/effort по типу и сложности задачи, доступности и ограничениям бюджета; итог и причина сохраняются |
| FR-16 | Изменение без остановки системы | Авторизованное изменение профиля применяется к **новым** attempts без перезапуска Kotlin-сервиса; текущие attempts сохраняют immutable снимок конфигурации |
| FR-17 | Capability validation и безопасный fallback | Перед запуском проверяются поддержка роли/модели/effort, наличие авторизации, доступность runtime и бюджет; несовместимость → понятный `BLOCKED` без расхода попытки; fallback — лишь из разрешённых профилей и при доказанной безопасности перехода |
| FR-18 | Изолированная рабочая среда агента | Агент получает достаточно прав **внутри sandbox** (код, build, зависимости, инструменты), но не получает host filesystem, host Docker socket, чужие репозитории и GitHub Publisher credentials; реальный Gate S0 обязателен до внедрения runtime |

## 5. Нефункциональные требования (целевые, подлежат согласованию)

- **Безопасность:** default DENY, отдельные полномочия исполнения и публикации; токены GitHub недоступны инструментам coding-агента; без произвольного root/shell из GitHub Issue.
- **Изоляция:** task-scoped workspace, запрет доступа к неразрешённым проектам и credentials; systemd/namespace/cgroups рассматриваются как Linux-механизмы, не функции Kotlin.
- **Надёжность:** транзакционная SQLite-база (миграции/WAL), однозначный владелец переходов, durable intent до внешнего действия; ambiguous outcome не превращать в PASS.
- **Наблюдаемость:** структурированные события с редактированием секретов, короткий API-статус, диагностика блокеров без необходимости читать многостраничные логи.
- **Развитие:** Agent Catalog, подключаемые adapters и настраиваемые профили/роли/модели/effort — первоклассные функции, не набор `if (agent == codex)`; Android получает доступ только через авторизованный API.
- **Управление ресурсами:** явные timeout, concurrency, max attempts, лимиты стоимости/токенов и допустимых усилий reasoning; значения должны быть измерены и утверждены для MVP.

## 5A. Дополнение — динамический выбор агентов, моделей и усилия рассуждения (DRAFT)

1. **Agent Adapter** — один интерфейс запуска, наблюдения, остановки и получения подтверждаемых артефактов для разных CLI/SDK. Новый адаптер не изменяет `WorkflowPhase`, SQLite lifecycle или издателя PR.
2. **Agent Catalog** — доступные/проверенные адаптеры, поддерживаемые ими роли, провайдеры, модели, reasoning effort (в том числе `high`/`xhigh`, **только если модель поддерживает**), инструменты и ограничения; фактическая совместимость определяется `preflight`, а не предположением.
3. **Agent Profile** — запись `profile_id + adapter_id + role + model + effort + runtime_profile + limits`. Owner может менять назначение профилей для Coding, Review, Planner и опционального Chief без правок кода и без перезапуска.
4. **Выбор на задачу:** `MANUAL` (владелец выбирает), `AUTO_RULES` (правила по типу/сложности) либо `AUTO_AI` (планировщик предлагает лучший вариант по запросу и ограничениям). **Автоматический селектор вправе выбирать только из явно разрешённых профилей**, не повышать права и не менять политику WORK/PERSONAL.
5. **Запись решения:** хранить выбор, версию профиля, model/effort, причину, expected cost/budget, идентификатор attempt и evidence. Смена роли/модели в ходе задачи допустима **между attempts**, а не внутри незавершённого процесса; независимость Review и соответствие exact tree обязательны.
6. **Ошибки и fallback:** недоступный агент/модель, unsupported effort или auth failure → понятная диагностика до попытки. Смена агента/модели автоматом допускается по заранее разрешённой политике и только при доказанном отсутствии неопределённого живого процесса; иначе `NEEDS_OWNER` по ADR-002.
7. **Поэтапное внедрение:** M1 — модель профилей/реестр и схема; M2 — первый настоящий Codex-adapter и Gate S0; M3 — независимый Review/Draft PR; M4 — второй реальный адаптер и автоматический выбор `AUTO_RULES`/`AUTO_AI` с E2E. Идея динамического выбора — **входит в целевой серверный MVP до Android**, а не в неопределённые будущие версии.

**Важно:** выбор модели/агента не означает выдачу новых OS/GitHub прав. Профиль доступа определяется доверенной project policy и sandbox. Конкретная модель адаптеров и route decision контракт согласуются в ADR-005; sandbox — ADR-003.

## 6. Не входит в MVP

Android-пульт, многомашинное распределение, Kubernetes, собственная LLM, автоматический Merge, **поддержка любого произвольного агента/модели без адаптера и проверенного доступа**, неограниченные self-healing/retries, автономный ChatGPT-Chief без проверенной интеграции. **Подключаемые адаптеры и динамический выбор среди поддержанных профилей входят в серверный MVP.**

## 7. Сценарии приёмки MVP

1. На разрешённом PERSONAL репозитории создаётся настоящая Issue.
2. Работа начинается без открытия терминала и без ручного запуска Codex.
3. Coding делает полезное изменение, независимо проверенное агентом.
4. DevOrchestrator публикует настоящий **Draft PR**, без Merge.
5. Пользователь получает короткий отчёт со ссылкой и проверяемыми результатами.
6. Повторный GitHub poll и рестарт управляющего сервиса не создают дублирующих агентов, commits, pushes или PR.
7. WORK-проект при аналогичном событии не запускается без Owner GO.
8. Невозможно добиться исполнения/публикации изменением текста Issue или сообщения агента.
9. Owner меняет Coding/Review агент, модель и effort в профиле без изменения workflow-кода и рестарта сервиса; новая попытка использует новую версию профиля, старые доказательства сохраняются.
10. Для двух задач система в AUTO-режиме выбирает подходящие профили из реального каталога как минимум двух проверенных adapters/agent profiles; выбор, причина и ограничения отражены в истории.
11. Недоступная модель, неподдерживаемый effort или неверный sandbox preflight приводят к читаемому BLOCKED **до попытки**, без выдачи агенту новых прав и без слепого fallback.
12. В изоляции агент действительно может установить разрешённые зависимости и собрать проект; попытка доступа к хосту/чужому репозиторию/ключам Publisher отклоняется.

## 8. Открытые решения M0

- ADR-002: **APPROVED** (R-01–R-06); технические контракты и реализация recovery зависят от ADR-003/004/005.
- ADR-003: полномочия, sandbox, токены и модель угроз.
- ADR-004: модель GitHub-интеграции и привязка к репозиторию/Issue/PR.
- ADR-005: AgentRunner, независимый Review, расширяемый Agent Catalog, динамическое назначение ролей/моделей/effort и AI Selection; число разрешённых коррекций фиксировано ADR-002.
- Точные пределы ресурсов, порядок Chief для WORK, API-аутентификация и политика хранения событий.

**Нельзя использовать этот черновик как разрешение на автоматический запуск или публикацию.**
