# DevOrchestrator — Техническое задание v0.1

**Статус:** DRAFT · **Этап:** M0 · **Дата черновика:** 2026-10-17.  
**Утверждённые части:** ADR-001 (Project Registry) и ADR-002 (Lifecycle/Recovery, R-01–R-06). PRD в целом остаётся DRAFT до финального согласования M0.

## 1. Зачем создаём

Система должна уменьшить ручную координацию ИИ-разработки: пользователь ставит задачу в ChatGPT или GitHub; DevOrchestrator сам находит подходящий разрешённый проект, запускает Coding, проверки, независимый Review и создаёт Draft PR. Пользователь следит за результатами и принимает решение о Merge. В дальнейшем — наблюдает и управляет с Android.

**Главный критерий пользы:** задача завершается полезным Draft PR, а не сотнями тестов самого оркестратора и ручной передачей промптов.

## 2. Границы MVP

- Одна управляющая машина Linux WORK; один основной Kotlin/JVM-сервис и одно авторитетное состояние.
- GitHub — источник задач и место публикации Draft PR.
- Coding-адаптер V1 — Codex CLI; независимый Review — отдельный контекст/сессия; конкретный reviewer адаптер ещё согласуется.
- Автоматическое исполнение допускается **только для явно зарегистрированных и разрешённых PERSONAL проектов** по ADR-001.
- Для WORK/1МТ — отдельное ручное Owner GO на запуск и публикацию.
- Owner всегда принимает Merge самостоятельно. По утверждённому ADR-002/R-04 Chief AI не обязателен до Draft PR в PERSONAL MVP; дополнительные gates определяет проектная политика.

## 3. Роли

- **Owner**: регистрирует проекты, управляет политиками, видит состояние, останавливает или разрешает операции.
- **Orchestrator**: принимает задачи, управляет состояниями, процессами, доказательствами, публикацией и восстановлением.
- **Coding Agent**: изменяет код в изолированной среде и сообщает конкретный результат.
- **Review Agent**: получает независимый снимок diff и проверяет изменения отдельно от Coding-сессии.
- **GitHub**: источник внешних идентификаторов задач и PR, не источник полномочий.

## 4. Функциональные требования

| ID | Требование | Критерий приёмки |
|---|---|---|
| FR-01 | Project Registry и политики (ADR-001) | Чужая/неизвестная Issue не запускается, разрешённая определяется по доверенному repo ID |
| FR-02 | GitHub intake | Новая разрешённая Issue появляется в SQLite ровно как одна логическая задача |
| FR-03 | Durable workflow | Фаза, попытка, события и результаты восстанавливаются после restart без повторного запуска |
| FR-04 | Coding | Система сама запускает реальный Codex и сохраняет статус, логи и diff |
| FR-05 | Verification | PASS, FAIL, NOT_RUN не смешиваются; команда/exit-code/артефакты связаны с попыткой |
| FR-06 | Independent Review | Отдельная сессия проверяет зафиксированный diff, а не самоотчёт Coding |
| FR-07 | Correction loop | Не более установленного проектом лимита; каждый повтор имеет уникальный attempt ID |
| FR-08 | Draft PR | После условий политики публикуется только Draft PR с проверяемым head/base; Merge запрещён |
| FR-09 | Recovery | При сомнительном внешнем эффекте система проверяет GitHub/Git, а не повторяет запись вслепую |
| FR-10 | Owner control | Владелец может видеть BLOCKED/UNKNOWN и приостанавливать новые действия |
| FR-11 | Compact status | Для задачи видны фаза, агент, тесты, PR, блокер и один следующий шаг |
| FR-12 | Audit trail | Изменение политики, решения и внешние эффекты имеют автора/время/идентификатор |

## 5. Нефункциональные требования (целевые, подлежат согласованию)

- **Безопасность:** default DENY, отдельные полномочия исполнения и публикации; токены GitHub недоступны инструментам coding-агента; без произвольного root/shell из GitHub Issue.
- **Изоляция:** task-scoped workspace, запрет доступа к неразрешённым проектам и credentials; systemd/namespace/cgroups рассматриваются как Linux-механизмы, не функции Kotlin.
- **Надёжность:** транзакционная SQLite-база (миграции/WAL), однозначный владелец переходов, durable intent до внешнего действия; ambiguous outcome не превращать в PASS.
- **Наблюдаемость:** структурированные события с редактированием секретов, короткий API-статус, диагностика блокеров без необходимости читать многостраничные логи.
- **Развитие:** добавление второго адаптера агента без изменения ядра; Android получает доступ только через авторизованный API.
- **Управление ресурсами:** явные timeout, concurrency, max attempts; значения должны быть измерены и утверждены для MVP.

## 6. Не входит в MVP

Android-пульт, многомашинное распределение, Kubernetes, собственная LLM, автоматический Merge, поддержка всех моделей/агентов, неограниченные self-healing/retries, автономный ChatGPT-Chief без проверенной интеграции.

## 7. Сценарии приёмки MVP

1. На разрешённом PERSONAL репозитории создаётся настоящая Issue.
2. Работа начинается без открытия терминала и без ручного запуска Codex.
3. Coding делает полезное изменение, независимо проверенное агентом.
4. DevOrchestrator публикует настоящий **Draft PR**, без Merge.
5. Пользователь получает короткий отчёт со ссылкой и проверяемыми результатами.
6. Повторный GitHub poll и рестарт управляющего сервиса не создают дублирующих агентов, commits, pushes или PR.
7. WORK-проект при аналогичном событии не запускается без Owner GO.
8. Невозможно добиться исполнения/публикации изменением текста Issue или сообщения агента.

## 8. Открытые решения M0

- ADR-002: **APPROVED** (R-01–R-06); технические контракты и реализация recovery зависят от ADR-003/004/005.
- ADR-003: полномочия, sandbox, токены и модель угроз.
- ADR-004: модель GitHub-интеграции и привязка к репозиторию/Issue/PR.
- ADR-005: AgentRunner, независимый Review и число разрешённых коррекций.
- Точные пределы ресурсов, порядок Chief для WORK, API-аутентификация и политика хранения событий.

**Нельзя использовать этот черновик как разрешение на автоматический запуск или публикацию.**
