# M4-01: ChatGPT → GitHub → автономный PERSONAL-исполнитель

Владелец обсуждает задачу в ChatGPT с телефона. ChatGPT уточняет результат и тесты,
показывает готовое ТЗ и **после подтверждения владельца** через уже подключённый GitHub
создаёт новый Issue в разрешённом личном репозитории с меткой `devorch:run`.
Сам ChatGPT не должен добавлять разрешение на основании текста чужого Issue.
Сервис забирает задачу и сохраняет результат в GitHub. По просьбе владельца ChatGPT
читает Issue/PR и объясняет результат. Новый ChatGPT API/MCP, Android или Web UI не нужны.

Короткие комментарии в Issue: принято, работаю, тесты, независимое ревью, готов Draft PR
либо остановлено с дальнейшим действием. Это источник статуса для ChatGPT.
Проактивная доставка сообщения в ChatGPT **не реализована**. GitHub mobile может
показывать уведомления согласно настройкам подписки владельца.
Merge всегда решает владелец.

## Что входит в реализацию

Обычная точка входа установленного Kotlin distribution:

```
dev-orchestrator-kotlin service /absolute/personal.properties
dev-orchestrator-kotlin run /absolute/personal.properties
dev-orchestrator-kotlin status /absolute/personal.properties
```

`service` работает постоянно; интервал поиска при простое/остановке/ошибке GitHub —
60–120 секунд (по умолчанию 90). Между стадиями уже принятой задачи задержки нет.
`run` выполняет один шаг для диагностики. `status` читает только локальную SQLite,
без токена, сети, восстановления или модели; работает и при занятой блокировке сервиса.
Без аргументов сохранён прежний HTTP health bootstrap для совместимости CI.
Автономный режим не открывает HTTP-порт.

Работает только фиксированный репозиторий
`siyovushdev/devorch-kotlin-e2e-smoke`, стабильный ID1424152600, default branch `main`.
Это намеренно ограниченный PERSONAL-пилот. WORK/1МТ и другие репозитории не поддержаны.
Допуск требует открытый Issue, автора `siyovushdev`, текущую метку `devorch:run`
и последнего подтверждённого автора её установки `siyovushdev` в полной ограниченной
истории событий. Токен интеграции ChatGPT должен действовать от этого владельца;
GitHub App/bot с другим actor пока не допускается. До первого запуска надо проверить,
что подключённая интеграция действительно умеет создавать Issue и ставить метку с такой
атрибуцией. Это не проверялось живой записью в данной разработке.

Каждая задача получает pin описания/base SHA, новый самостоятельный checkout и свою
SQLite/артефакты. Повтор Issue, перезапуск и закрытый/изменённый/лишённый разрешения Issue
не создают новую попытку. Изменение описания, имени или закрытие после pin требует
вмешательства; комментарии сервиса не считаются изменением ТЗ (`updated_at` игнорируется
при сравнении принятой задачи). Новое ТЗ оформляется новым Issue после решения владельца.
Новые задачи никогда не запускаются из текста/команды/URL в чужом Issue.
Текущий reader имеет пилотный предел: до пяти страниц по 100 элементов общей истории
Issues/PRs (`state=all`). Если история достигает 500 записей, discovery останавливается
без частичного intake; нужны отдельное расширение пагинации и проверка. События метки
также ограничены десятью страницами; неполная история не выдаёт разрешения.

Переиспользованы существующие CodingAttemptJournal, NativeCodingRunner/супервизор,
WorkflowEngine, контроллерный Python unittest, frozen candidate и guarded Publisher.
Удалена привязка Coding к Issue #1; Publisher получает выбранный номер, сохраняя
прежний default для старых opt-in smoke. Выполняются одна Coding-сессия, реальные
контроллерные тесты, новая read-only Review-сессия и до двух исправлений. Публикация
только Draft PR с проверкой remote tree, parent, ref, base, номера и URL.
Owner callback Publisher сохраняется и перепроверяет текущую локальную конфигурацию
и GitHub-разрешение на границах внешних эффектов. Аналогичная проверка добавлена перед
запуском Coding/Tests/Review. Снятие разрешения не отменяет уже отправленный запрос;
неподтверждённое действие переводится в остановку.

Тестовая команда фиксирована: защищённый контроллерный harness Python unittest из #39,
поиск `tests/test*.py`, с минимумом тестов из локальной конфигурации. Произвольные команды
из Issue не исполняются. MVP не устанавливает зависимости проекта, поддерживает только
офлайн Python stdlib unittest. Модель и тестовый контракт задаются локально владельцем.
Лимит каждой модели/контроллерного теста — 120 секунд; денежный лимит не обеспечен
провайдером. Отмечать только небольшие задачи, соответствующие этому контракту.

## Сохранение и восстановление

В корне состояния лежат `service.db` и `service.lock`; рядом `task-<githubIssueId>/`
с `run.db`, checkout, artifacts, snapshots и publisher. Старые smoke DB/директории
не используются и не мигрируются этим сервисом. Каждая новая task DB использует
существующую схему v7; её консервативное ограничение одной публикации на репозиторий
сохраняется внутри одной задачи. Общая очередь допускает ровно одного worker на
весь корень состояния (OS file lock на всё время жизни процесса).

Не запускать второй экземпляр с другим корнем для того же репозитория: распределённой
блокировки между разными установками/компьютерами нет. Владелец выбирает один HOME root.
Не удалять базы, holds, intents, reservations или артефакты ради «повтора».

После перезапуска `accepted` продолжается; прерванная подготовка checkout удерживается,
не повторяется. Сохранённые завершённые стадии продолжаются через прежний engine.
STARTING/RUNNING Coding, Tests/Review и SENDING публикации восстанавливаются как
UNKNOWN/UNCERTAIN + NEEDS_OWNER. Ни новая модель, ни PUSH/POST вслепую не повторяются.
Любая остановленная задача блокирует **всю** очередь, включая отдельные task DB:
старый процесс мог ещё существовать. Не подтверждённая отправка комментария также
сохраняется заранее и после сбоя не повторяется. На каждую стадию не более одного
комментария, исправления не создают шквал повторных статусов.

Восстановление UNKNOWN намеренно не автоматическое. Владелец/сопровождающий проверяет
локальный `status`, процесс/cleanup и GitHub-результаты, сохраняет доказательства.
Read-only reconciliation Publisher не снимает hold. В MVP нет команды принудительного
retry/reset/resume: после ручного разбора нужен отдельно согласованный путь продолжения.
Обычные успешно завершённые задачи вмешательства не требуют.

## Однократная подготовка HOME — только с отдельным разрешением

**Эти действия не выполнены и не разрешены данным source PR.**

1. Владелец утверждает проверенную версию и отдельно разрешает установку/включение
   постоянного PERSONAL-сервиса, реальные модели и Draft-публикации для указанного repo.
   Никакого Merge или расширения WORK-политики из этого решения не следует.
2. Под выделенным `devorch-e2e` подготовить одну установку distribution (JDK21),
   отдельные sibling state/agent-home, state mode700; `.codex` в agent-home — только
   нужные model credentials/config. Owner config и GitHub credentials хранятся вне
   checkout и agent-home. Пример: `config/personal.properties.example`, изначально OFF.
   Файл конфигурации должен быть canonical, owned by текущий user, mode600.
3. Проверить доступный Codex CLI/matching code-mode-host, модель, офлайн Python3,
   git и локальный proxy. Профили/flags проверяются runtime, но доступность настоящей
   модели подтверждается только живой приёмкой. Существующие HOME-артефакты не трогать.
4. Приватно предоставить fine-grained GitHub PAT только этого repo: Metadata(read),
   Contents(read/write), Issues(read/write), Pull requests(read/write), срок действия.
   `controller.env` mode600: `DEVORCH_PERSONAL_TOKEN=<private value>`.
   Не вставлять токен в чат, Issue, Git, unit-файл или аргументы CLI.
   Fetch/PUSH получают секрет через privateEnvironment супервизора, сохранённый
   launch JSON и Coding/Review/Tests его не получают. Переменные окружения не являются
   ОС-изоляцией от процессов того же UID: сохраняются требования защищённого контроллера
   и изолированного PERSONAL-аккаунта из #38–#40. Не хранить там рабочие секреты.
5. После GO изменить `enabled=true`; проверить пути в
   `packaging/devorch-personal.service.example`, затем установить user unit.
   `systemd --user` restart использует control-group и UMask0077.
   Автозапуск **после reboot без входа пользователя** требует отдельно разрешённого
   linger/user-manager решения; пример сам его не включает и этого не обещает.
   Не добавлены install/enable скрипты или startup hook.
6. Проверить живую приёмку: с телефона обсудить и подтвердить новое ТЗ в ChatGPT;
   интеграция создаёт новый Issue и owner-метку. Для этой задачи терминал не нужен.
   Сервис сам открывает один Draft PR. Проверить реальные тесты, отдельную Review-сессию,
   точные GitHub tree/ref/parent и штатный restart без дублей.

До этой приёмки **live unattended acceptance NOT_RUN**. Прямой ввод Issue в GitHub —
только запасной тест intake. Успех прежнего разового E2E не заменяет приёмку сервиса.

## Проверки разработки

Offline tests используют fake GitHub/модель, настоящие disposable Git/SQLite/Python
и супервизор. Проверяются новая Issue #17, следующая #18, исправление, restart после
завершённых стадий, повтор polling, один worker, потеря ответа/POST-intent, снятие
разрешения, изменение ТЗ, запрет чужой атрибуции, bound истории событий и блокировка
очереди. Старые crash/uncertainty регрессии engine/publisher сохранены.
CI собирает distribution, выполняет все обычные тесты, прежний HTTP smoke и отдельный
read-only GitHub intake smoke. Реальный сервис/модели/PUSH/POST в CI не включаются.
Совместимость с #26 проверяется отдельно в disposable copy, без Merge.
