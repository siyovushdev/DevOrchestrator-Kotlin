# ADR-003 — безопасность без повторения permission-блокировок

> **Текущее решение для MVP: S-04 — Native Codex CLI (APPROVED, 2026-10-17).**
> [Поправка S-04](ADR-003-MVP-native-cli-decision.md) **заменяет Docker Sandboxes microVM (S-01/S-02) как обязательный runtime первого MVP**. Используем установленный Codex CLI в обычном пользовательском сеансе, native sandbox и временную копию только личного тестового проекта. Никакой дополнительной Linux-учётной записи, Docker/microVM или VM Gate S0 на пути первой задачи. **Под одним UID нет гарантии недоступности хостовых файлов/credential stores**; WORK/1МТ в Native MVP не допускать. Docker/S-01/S-02/S-03 остаются историей и вариантом будущего усиленного профиля. ADR-003 в целом DRAFT до закрытия оставшихся решений.


**Статус:** DRAFT — **S-04 APPROVED для Native MVP**; ранее утверждённые S-01/S-02 Docker перенесены за рамки первого MVP. Остальные детали безопасности не утверждены.  
**Этап:** M0, [Issue #3](https://github.com/siyovushdev/DevOrchestrator-Kotlin/issues/3).  
**Основа:** ADR-001 и ADR-002 — APPROVED. **Не разрешает написание кода, создание runtime grants или запуск агентов.**

## 1. Цель

У DevOrchestrator должны быть реальные границы безопасности, не блокирующие уже подтверждённое выполнение. Избегать самодельного многослойного управления Linux sandbox, множества несовместимых конфигураций и вручную создаваемых per-Issue launch scripts/approvals. Ошибка прав — диагностируемый отказ **до потребления попытки**, а не повод очищать state.

## S-01 — первоначальный выбор Docker microVM (APPROVED исторически; SUPERSEDED для MVP решением S-04)

**Решение владельца:** основной runtime для Coding/Review и последующих поддерживаемых AI-агентов — **готовые Docker Sandboxes (`sbx`) с microVM**, при условии фактического **Gate S0 PASS** на рабочей машине. Для каждой задачи/сессии используем изолированную копию соответствующего проекта (предпочтительно `--clone`); вывод diff/artifacts передаём доверенному Controller/Publisher через проверяемый и ограниченный путь.

1. **Свобода внутри VM:** агент может выполнять терминальные команды, менять исходники *в копии*, устанавливать зависимости, использовать `sudo` и частный Docker Engine *внутри microVM*, собирать/тестировать проект. При работе через `sbx` внутренняя песочница Codex может быть отключена, **но только в проверенной VM-изоляции**. Не создавать второй конфликтующий permission/sandbox engine.
2. **Без доступа к хосту:** не прокидывать host Docker socket, writable рабочий каталог хоста, `SSH_AUTH_SOCK`, ключи публикации, служебные MCP/SSH-инструменты с host powers, чужие проекты; по умолчанию отказаться от общего host skills mount (`--skills=off`, при поддержке версии). Сеть контролируется исходящей политикой, доступ к провайдерам моделей и пакетным репозиториям проверяется.
3. **Отдельный Publisher:** только доверенный компонент Kotlin-сервиса за границей agent VM владеет GitHub publication credentials и может выполнить Commit/Push/**Draft PR** после PASS всех нужных проверок. Никакого автоматического Merge.
4. **Много агентов:** Codex, Cursor, Claude, Gemini и другие совместимые с `sbx` используют **один тип изоляции**, но каждому агенту всё равно требуется проверенный CLI/adapter, модель, auth и отдельный независимый Review-контекст. Kimi или любой иной отсутствующий в каталоге агент допускается только после проверенной кастомной интеграции.
5. **Обязательная проверка до исполнения:** Gate S0 должен подтвердить Ubuntu/KVM/доступ к VM, реальный login/inference, код/Gradle/build, сбор артефактов, stop/cleanup, host boundary и network policy. До PASS статус исполнения `NOT_READY`, не делать настоящую task attempt и не считать Docker Sandboxes внедрённым.
6. **При несовместимости:** зафиксировать конкретный S0 FAIL, не подменять runtime обычным привилегированным `docker run`, host Codex `--dangerously-bypass...` или другим незащищённым fallback. Альтернатива требует отдельного согласования владельца в ADR-003.
7. **Не путать изоляцию с доверием:** даже sandbox с sudo и разрешённой сетью способен посылать данные на разрешённые адреса; код, секреты и egress нужно ограничивать перед передачей агенту. Ключи Publisher в VM не передавать.

**Статус решения:** S-01 APPROVED как стратегия; Docker Sandboxes **не установлен и не проверен на WORK**. Полный ADR-003 DRAFT до согласования authority/security details и Gate S0; начало Kotlin-разработки требует завершения M0.

## S-02 — Docker-специфический усиленный профиль (APPROVED исторически; SUPERSEDED для MVP решением S-04)

Подготовлена подробная [модель S-02: чистый staging, файловые права, отключение host SSH/MCP/skills, сеть, контролируемая передача diff/artifacts и Gate S0](ADR-003-S02-access-and-artifacts-DRAFT.md).

**Критичное уточнение по Docker:** `sbx --clone` защищает оригинальный host repository **от записи, но не от чтения** — внутри VM доступен `/run/sandbox/source`, включая ignored/untracked файлы. Поэтому в S-02 предлагается монтировать **только временный чистый staging Git repo**, а не обычный рабочий checkout с `.env`, токенами и скрытыми файлами. Default SSH agent forwarding и возможные host-side MCP/skills также необходимо явно исключить/проверить.

**Статус:** S-01 APPROVED как стратегия Docker Sandboxes; **S-02 APPROVED**; оставшиеся решения ADR-003 требуют согласования. Запуск и установка на WORK не производились.

## S-03 — Docker Gate S0 (DRAFT; DEFERRED после решения S-04)

Подготовлен [короткий план Gate S0](ADR-003-S03-gate-s0-DRAFT.md): пять групп проверок покрывают десять сценариев S-02, реальный Codex и VM проверяются **один раз при интеграции** (и при существенных изменениях runtime), **не перед каждой задачей**. Один целевой цикл устранения диагностированной несовместимости; при повторном отказе — отдельное Owner-решение, без бесконечных обходов.

**S-03 пока не утверждён и не выполнялся.** Это предложение о процедуре, не разрешение на изменение конфигурации WORK.
## 2. Предлагаемые границы доверия

| Роль | Разрешено | Не разрешено |
| --- | --- | --- |
| Owner | Утверждать/менять Project Registry и WORK approvals через аутентифицированный API | Выдавать полномочия текстом Issue/ответом агента |
| Kotlin Controller | Сверять project/repo ID, управлять workflow, durable attempts/effects и политиками | Исполнять произвольную shell-команду из Issue; считать Codex PASS авторизацией |
| AgentRunner (Coding) | Только изолированная копия выбранного проекта, нужные build tools, inference | Доступ к 1МТ/Production, чужим workspace, токенам публикации и контроллеру |
| Independent Review | Read-only/frozen diff/tree, отдельная сессия и необходимые read-only проверки | Подменять результат Coding, изменять reviewed tree, публиковать |
| Trusted Publisher | После проверенных gates — exact Commit/Push/Create **Draft PR** по одной разрешённой ветке | Исполнять agent commands, force push, Merge, произвольные GitHub операции |

Интерфейсное разделение Kotlin-классов не равно изоляции ОС: worker не должен иметь тот же доступ к секретам Publisher через общие файлы/UID/процессы. Потребуются проверенные OS/VM credentials boundaries.

## 3. Project policy и жизненный цикл полномочий

- **PERSONAL:** явно разрешённый проект автоматически проходит Coding → Review → Draft PR, без per-Issue Owner GO и ручных запусков, в рамках заранее утверждённой project policy.
- **WORK:** start и publication требуют отдельных Owner GO; неизвестные проекты default DENY.
- Execution permission применяется только для актуальной попытки; completed Coding/Review сохраняют подтверждённые результаты. Его истечение **не аннулирует** reviewed tree, PASS и исторические receipts.
- Publication разрешается **отдельной policy** на основании точной актуальной Issue/repo/tree/branch, успешных Verification и независимого Review; не требует «продлить старое execution разрешение».
- Подтверждённые старые attempts не становятся новыми grants. При UNKNOWN действует ADR-002: scoped hold + доказательный recovery, без blind retry.
- Для одного ресурса один авторитетный владелец переходов/исполнения; SQLite — долговременный источник состояний, а не набор внешних lock/claim JSON-файлов.

## 4. Не писать собственный sandbox engine

**Выбранный основной кандидат S-01 (APPROVED как стратегия):** Docker Sandboxes `sbx` в изолированной microVM. Его фактическая пригодность **условна до Gate S0 PASS** (KVM/Ubuntu, CLI, clone mode, credentials и необходимые ресурсы).

**Запасной вариант (не утверждён к использованию):** Codex native sandbox `workspace-write` под отдельной низкопривилегированной OS-учётной записью. Рассматривать только после S0 FAIL и **отдельного согласования Owner**, без самодельного наложения AppArmor/bubblewrap/systemd профилей.

**Стратегия A утверждена (S-01); эксплуатационная готовность ещё не доказана.** Ранее зафиксированные блокеры systemd/`/proc/self/exe`, двойного sandbox и авторизации — обязательные отрицательные сценарии. Не считать документацию или unit-тесты заменой Gate S0.

Правило secrets: publisher GitHub token хранится только вне AgentRunner/agent VM; inference credentials отделены. Приватный исходный код допускается только в доверенную изолированную копию. Любые MCP/SSH/host-mounted sockets и shared directories считаются потенциальным выходом за границу и запрещены по умолчанию.

## 4A. Docker microVM — исторический вариант S-01/S-02 (DEFERRED для первого MVP)

**Согласованный для проверки вариант — Docker Sandboxes (`sbx`), не обычный Docker-контейнер.** Согласно документации Docker, `sbx` использует отдельную microVM, где агент имеет `sudo`, может устанавливать инструменты и запускать внутренний Docker Engine. Изоляция хоста обеспечивается границей VM и настройкой того, какие ресурсы реально переданы внутрь. Не считать документированную поддержку доказательством совместимости с конкретным WORK-хостом: требуется Gate S0.

Предлагаемый простой execution profile:

1. **Код:** `clone mode` (`sbx ... --clone`) или mountless + явный import только нужного проекта. Не использовать direct read/write mount основного рабочего дерева для недоверенного Coding.
2. **Разрешено внутри VM:** shell, package managers, Java/Kotlin/Android SDK и build tools, временные каталоги, тесты, локальные контейнеры и запись файлов проекта. При необходимости `sudo` — **только внутри VM**.
3. **Не передавать:** host root filesystem, host Docker socket, приватные репозитории вне scope, GitHub Publisher/WORK токены, Tailscale/SSH credentials, `SSH_AUTH_SOCK`, host-side MCP tools с доступом к системе; shared skills host mount отключать либо подвергать отдельной оценке (`--skills=off`, если поддерживается установленной версией).
4. **Сеть:** доступ к поставщику модели и зависимостям ограниченным policy allowlist; заранее проверить, что Android/Gradle/Maven и inference действительно работают. Слишком узкий список сайтов не должен приводить к бесконечным ложным attempts.
5. **Результат:** чтение artifacts/diff через ограниченный экспорт; Publisher — отдельный доверенный компонент с собственными полномочиями. VM можно удалить после confirmed cleanup и соблюдения R-05.
6. **Нет повторных запросов:** в предварительно разрешённом PERSONAL режиме агент может работать автономно внутри sandbox, в том числе с режимом без интерактивных approvals, **только после реального Gate S0**. Нельзя переносить этот режим за пределы VM.

`sbx` сейчас поддерживает несколько coding agents (Codex, Cursor, Claude, Gemini, OpenCode и др.). Разные модели/effort выбираются **на уровне их адаптеров/профилей** и предварительно валидируются; не считать experimental `sbx --model` универсальным способом выставлять reasoning effort у всех агентов. Изменение агента/модели не увеличивает доступ к хосту и не меняет доверенную project policy.

**Ссылки для проверки реализации:** [Docker Sandbox Security](https://docs.docker.com/ai/sandboxes/security/), [Clone mode](https://docs.docker.com/ai/sandboxes/security/isolation/), [Linux prerequisites](https://docs.docker.com/ai/sandboxes/install/), [Supported agents](https://docs.docker.com/ai/sandboxes/agents/). Для Linux local `sbx` требуется Ubuntu 24.04+ и работающий KVM, что нужно проверить на реальной машине. **Выбор S-01 утверждён как первоочередной; фактический deployment остаётся DRAFT до Gate S0 PASS.**

## 5. Preflight-first: обязательный Gate S0 перед реализацией AgentRunner

До разработки orchestration вокруг выбранного runtime провести ограниченную проверку **реального Codex в той же конфигурации, в которой он будет выполняться**:

1. На WORK: реальный sandbox и изоляция от production, чужих репозиториев и GitHub publication credentials.
2. Доступность `/proc/self/exe`, нужных системных вызовов, временного writable каталога, Git, сети/model inference и аутентификации.
3. Реальный безвредный coding + read-only independent review на временном личном тестовом репозитории, с проверенным stdout/artifacts.
4. Доказанное завершение агента и потомков; timeout/stop/cgroup/VM cleanup на тестовых процессах, без сигналов чужим PID.
5. Повтор проверки после restart и проверка limits; негативная проба доступа к запрещённым путям/секретам.
6. При FAIL — **не потреблять workflow attempt, не запускать новую Issue, не ослаблять случайно sandbox**. Сначала документировать конкретную несовместимость и выбрать поддерживаемый runtime; не строить собственный патч-движок.

Gate S0 должен выполняться до полноценного M2 AgentRunner, а его API/shape должен стать частью ADR-005. На этом этапе — только документируем требования, не устанавливаем новые службы.

## 6. Безопасный пользовательский результат

- Обычные PERSONAL задачи не запрашивают подтверждение на каждую попытку. Agent Profile может назначать разные CLI/роли/модели/effort без выдачи дополнительных прав OS/GitHub и без пересоздания runtime-политики для каждого изменения модели.
- При штатном PASS исполнитель автоматически переходит к независимому Review и публикации Draft PR.
- Если preflight недостаточен: `BLOCKED: SANDBOX_INCOMPATIBLE` с одним конкретным объяснением — без создания claim/attempt.
- Если позже фактически возник UNKNOWN: `NEEDS_OWNER` только у затронутой задачи и ресурсов; состояние REVIEW/PR не уничтожать.
- Контроллер никогда не снимает уже записанные holds по истечению времени или исчезновению PID.

## 7. Требования к приёмке

- Разрешённый PERSONAL repo → настоящий Codex + Review + Draft PR без ручного runtime GO.
- WORK без Owner GO → нет ни исполнения, ни публикации.
- Agent пытается читать publisher token / чужой проект → отказ проверен в реальном runtime.
- Настоящий Codex работает в выбранном sandbox, а не только mocked/test binary.
- Permission/config error диагностируется **до** создания durable attempt/claim.
- После успешного Review отозванное или истёкшее право на новое Coding не блокирует отдельно разрешённый Draft PR, если все актуальные publication guards проходят.
- Crash/неопределённость не создают вторую попытку/PR, история сохраняется, изоляция по ADR-002/R-01.

**Открыто на согласование:** результаты Gate S0 и конкретные ресурсы WORK; точная OS/VM boundary для Kotlin Controller/Runner/Publisher, хранение credentials, cleanup, сетевые правила, лимиты KVM/памяти для Android-сборок и fallback после несовместимости. **S-01 APPROVED, ADR-003 в целом DRAFT.**
