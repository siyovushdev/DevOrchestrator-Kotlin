# ADR-002 — Жизненный цикл задачи и восстановление после сбоев

**Статус:** APPROVED — владелец согласовал R-01–R-06 2026-10-17. **Этап M0; начало разработки не разрешено.**

## Проблема

В прежнем Python DevOrchestrator старые/неизвестные попытки, исторические наблюдения и истекающие разрешения могли блокировать уже завершённые задачи. В новом продукте необходимо разделить «выполнение агента», «разрешение» и «публикацию результата».

## Согласовано частично — R-01: локализация блокировок

**R-01 — APPROVED владельцем, 2026-10-17.** Если одна задача или её внешняя операция попала в `UNKNOWN`/`UNCERTAIN`, DevOrchestrator блокирует **эту задачу и все реально затронутые общие ресурсы** (например, тот же workspace, ветку или репозиторий), **но не останавливает независимые проекты и весь управляющий сервис**.

- Разграничение ресурсов проверяется по доверенной конфигурации и доказательствам владения, а не по тексту Issue.
- При недоказанной независимости ресурса допускается расширить область блокировки до него; при угрозе безопасности общей инфраструктуры — до необходимой общей границы. Нельзя объявлять изоляцию успешной без доказательств.
- `UNKNOWN` не преобразуется в `FAILED`/`SUCCEEDED`, не удаляется и не обходит cleanup/owner gates ради возобновления.
- Независимые задачи продолжат работу только если их execution и publication не зависят от заблокированных ресурсов.

**R-01–R-06 утверждены.** Полная таблица переходов и сценарии crash/recovery — в связанном R-06. Реализация Linux sandbox, привилегий Chief/Owner и GitHub API требует отдельных ADR-003/004/005.

### R-02 — доказательное автоматическое восстановление (APPROVED, 2026-10-17)

**После сбоя, перезапуска или потери ответа DevOrchestrator сначала восстанавливает сохранённые факты и проверяет реальное состояние, а не повторяет действие.**

- Сопоставляет durable workflow/attempt/effect IDs, generation, зарегистрированный проект, репозиторий и подтверждённые результаты с процессами и/или Git/GitHub. Текст ответа агента сам по себе не является доказательством завершения.
- **Если результат однозначно подтверждён**, продолжает с сохранённого этапа без повторного запуска уже выполненного Coding/Review и без повторной отправки подтверждённого Commit/Push/PR.
- **Если реальное состояние нельзя достоверно установить**, фиксирует блокер `NEEDS_OWNER`, сохраняет историю и запрещает слепой повтор запуска или публикации. Область блокировки ограничивается правилом R-01; связанные с неопределённым процессом общие ресурсы остаются защищёнными.
- Истечение разрешения не удаляет подтверждённые результаты; новое исполнение и публикация всё равно требуют действующих полномочий по отдельным политикам. Изменение состояния и разрешений ради «починки» без доказательств запрещено.
- Обязательная таблица переходов и сценариев отказов F01–F20 утверждена в R-06. Конкретные источники process/Git/GitHub evidence и execution-границы раскрываются в ADR-003/004/005.

**R-02 является обязательной частью утверждённого ADR-002; отдельного разрешения на реализацию это решение не выдаёт.**

### R-03 — не более двух автоматических исправлений после Review (APPROVED, 2026-10-17)

**На одну Issue допускается максимум два автоматических цикла исправления по замечаниям независимого Review.**

- Начальная пара Coding → Review не считается циклом исправления.
- Один цикл исправления состоит из новой попытки Coding для устранения замечаний и **нового независимого Review** актуального результата. У попыток собственные идентификаторы, результаты и привязка к версии проверяемого дерева.
- Если независимый Review возвращает PASS на любом этапе — система продолжает по остальным условиям политики проекта.
- После двух циклов, если Review снова не пройден, workflow переходит в `NEEDS_OWNER`. Самостоятельный третий цикл запрещён; владелец принимает дальнейшее решение отдельно.
- Политика проекта вправе установить более строгий предел (0 или 1), но не может незаметно превысить утверждённый максимум 2.
- Инфраструктурный сбой/`UNKNOWN` не даёт права «попробовать ещё раз» как исправление Review: действуют R-01 и R-02 с доказательным восстановлением.
- Счётчик циклов сохраняется в SQLite и переживает restart; повторное получение Issue или замечания не обнуляет лимит.

**R-03 является обязательной частью ADR-002 и не разрешает запуск реализации.**

### R-04 — Chief Review не блокирует Draft PR по умолчанию для PERSONAL (APPROVED, 2026-10-17)

**PERSONAL:** для явно зарегистрированного и разрешённого проектной политикой автоматического исполнения после успешных Coding, требуемых тестов и независимого Review PASS DevOrchestrator **автоматически создаёт Draft PR**, без обязательного предварительного Chief Review.

- Дополнительный Chief Review может проводиться **после создания Draft PR** как необязательная дополнительная проверка. Его отсутствие само по себе не задерживает Draft PR в стандартном PERSONAL режиме.
- Другие необходимые проверки, ограничения прав, подтверждение reviewed tree, действующий допуск публикации и корректные Git/GitHub-идентификаторы остаются обязательными; правило не разрешает обходить безопасность или публиковать неуспешно проверенный код.
- Draft PR — предложение изменений, а не Merge. **Автоматический Merge запрещён**; решение владельца обязательно.
- **WORK (включая 1МТ):** Chief Review и дополнительные Owner Gates определяются строгой **политикой конкретного проекта**. По ADR-001 запуск и публикация требуют отдельных Owner GO. Переход PERSONAL в автоматическую публикацию не даёт аналогичных полномочий WORK.

**R-04 утверждает порядок Chief/Draft PR.** Технический контракт доверенных решений, GitHub-публикации и отмены прав согласовывается отдельно в ADR-003/004.

### R-05 — сроки хранения истории и безопасная очистка (APPROVED, 2026-10-17)

**Утверждённые сроки хранения после успешного завершения и при отсутствии открытых рисков восстановления:**

| Категория данных | Срок |
| --- | --- |
| Полные логи выполнения агентов | **30 дней** |
| Временные рабочие копии исходников и изолированные snapshots | **7 дней после подтверждённого завершения** |
| История задач, решения владельца и сведения о Pull Requests | **1 год** |
| Доказательства `UNKNOWN`, `UNCERTAIN` и незавершённых операций | **До подтверждённого разрешения ситуации**, независимо от обычного срока |

- Истечение срока **не является разрешением на удаление**. До очистки проверяются терминальное состояние, отсутствие активных/неопределённых процессов, неразрешённых эффектов и необходимость данных для восстановления.
- Не удалять artifacts, claims, журналы и доказательства, которые связывают актуальную задачу, её Code/Review и GitHub-публикацию. Объекты, общие для нескольких задач, сохраняются до завершения всех зависимостей.
- Очистка должна быть проверяемой и ограниченной точным набором разрешённых путей, с записью события об удалении. Не применять `rm -rf` к нераспознанным каталогам и не удалять GitHub Issue или PR.
- Для истории с истёкшим годичным сроком применяется то же условие безопасной очистки; пока существует нерешённый блокер или потребность в recovery, соответствующие записи сохраняются.
- Квоты хранилища, формат архивов, резервные копии, защита персональных данных и процедура плановой очистки будут отдельно определены в технической спецификации перед реализацией. R-05 сам по себе не разрешает запуск задач очистки.

**R-05 — утверждённая часть ADR-002; численные квоты и технические механизмы очистки согласуются перед реализацией.**

### R-06 — утверждённая модель переходов и recovery (APPROVED, 2026-10-17)

Утверждён подробный [контракт R-06: Workflow/Attempt/Effect, отдельные holds, 20 сценариев сбоев и критерии тестирования](ADR-002-R06-state-machine-DRAFT.md).

**R-06 утверждён:** `DRAFT_PR_CREATED` — терминальный результат серверного MVP; `NEEDS_OWNER` — отдельный hold без потери фазы и подтверждённых результатов. Merge выполняет только владелец. Все R-01…R-06 обязательны.

## Утверждённая сводная модель

### 1. Три независимых слоя состояния

- **WorkflowPhase:** `QUEUED`, `CODING`, `VERIFYING`, `REVIEWING`, `READY_FOR_PR`, `PUBLISHING`, `DRAFT_PR_CREATED`, `FAILED`, `CANCELLED` (R-06).
- **AttemptState:** `PLANNED`, `STARTING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `UNKNOWN`, `CANCELLED`. Каждый Coding/Review запуск имеет независимый attempt ID и поколение.
- **EffectState:** `PREPARED`, `SENDING`, `CONFIRMED`, `REJECTED`, `UNCERTAIN`; отдельно для Commit/Push/PR.

`WorkflowHold`: `NONE`, `PAUSED`, `NEEDS_OWNER` — отдельное измерение, не удаляющее прогресс. `UNKNOWN` не означает FAILED/PASS и не обнуляется. Выполнение терминально завершается отдельно от полномочий на публикацию.

### 2. Переходы и восстановление

- Перед любым внешним write фиксировать durable intent с точным scope и уникальным effect ID.
- После restart сначала **сверять фактические процесс/Git/GitHub evidence**; не запускать новую попытку из-за отсутствия ответа.
- Подтверждённый старый Review не имеет права автоматически испортить актуальное Review; но любой текущий UNKNOWN/AMBIGUOUS ownership удерживает безопасность.
- После законченного Coding/Review публикация получает отдельное ограниченное разрешение согласно политике; истечение execution permit не должно стирать Chief/Owner решения и проверенный tree.
- Запрещено удалять holds/claims ради устранения симптомов. Recovery должен иметь явный контракт на конкретную неопределённость и оставлять аудит.
- При превышении correction limit -> `NEEDS_OWNER`, а не бесконечный цикл.

### 3. Наблюдаемость

У каждой Issue короткий ответ: `этап / текущий attempt / тесты / blocker / next action / ссылка PR`. Подробный журнал отдельно.

## Принятые решения и граница ADR

1. **Решено — R-04 (APPROVED):** для PERSONAL автоматический Draft PR после PASS независимого Review без обязательного предварительного Chief; для WORK — отдельная строгая политика проекта.
2. **Решено — R-03 (APPROVED):** максимум 2 автоматических цикла Coding → независимый Review после замечаний; далее `NEEDS_OWNER`.
3. **Решено — R-01 (APPROVED):** блокировать затронутую задачу и общие ресурсы, не останавливая доказанно независимые проекты. Конкретные критерии доказательства независимости разрабатываются далее.
4. **Решено — R-05 (APPROVED):** полные логи 30 дней; временные исходники 7 дней после завершения; история задач/решений/PR — 1 год; UNKNOWN и незавершённые операции — до подтверждённого разрешения. Очистка допускается только после проверки безопасности.

**ADR-002 APPROVED.** Полные переходы и F01–F20 — в R-06. Конкретные механизмы безопасности, GitHub и агентов требуют ADR-003/004/005 и финального утверждения M0. **Этот ADR сам по себе не разрешает писать код или запускать агентов.**
