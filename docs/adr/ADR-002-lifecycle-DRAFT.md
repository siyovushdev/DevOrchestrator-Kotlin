# ADR-002 — Жизненный цикл задачи и восстановление после сбоев

**Статус:** DRAFT — согласование продолжается; **R-01 APPROVED**. **Этап M0.**

## Проблема

В прежнем Python DevOrchestrator старые/неизвестные попытки, исторические наблюдения и истекающие разрешения могли блокировать уже завершённые задачи. В новом продукте необходимо разделить «выполнение агента», «разрешение» и «публикацию результата».

## Согласовано частично — R-01: локализация блокировок

**R-01 — APPROVED владельцем, 2026-10-17.** Если одна задача или её внешняя операция попала в `UNKNOWN`/`UNCERTAIN`, DevOrchestrator блокирует **эту задачу и все реально затронутые общие ресурсы** (например, тот же workspace, ветку или репозиторий), **но не останавливает независимые проекты и весь управляющий сервис**.

- Разграничение ресурсов проверяется по доверенной конфигурации и доказательствам владения, а не по тексту Issue.
- При недоказанной независимости ресурса допускается расширить область блокировки до него; при угрозе безопасности общей инфраструктуры — до необходимой общей границы. Нельзя объявлять изоляцию успешной без доказательств.
- `UNKNOWN` не преобразуется в `FAILED`/`SUCCEEDED`, не удаляется и не обходит cleanup/owner gates ради возобновления.
- Независимые задачи продолжат работу только если их execution и publication не зависят от заблокированных ресурсов.

**Остальные правила ADR-002 остаются DRAFT.** В частности, не утверждены полные состояния, crash recovery, correction limits, Chief-политика и сроки хранения.

## Предлагаемое решение

### 1. Три независимых слоя состояния

- **WorkflowPhase:** `QUEUED`, `CODING`, `VERIFYING`, `REVIEWING`, `READY_FOR_PR`, `DRAFT_PR_CREATED`, `AWAITING_OWNER`, `DONE` (конкретный enum ещё согласуется).
- **AttemptState:** `PLANNED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `UNKNOWN`. Каждый Coding/Review запуск имеет независимый attempt ID и поколение.
- **EffectState:** `PREPARED`, `SENDING`, `CONFIRMED`, `REJECTED`, `UNCERTAIN`; отдельно для Commit/Push/PR.

`UNKNOWN` не означает FAILED/PASS и не должен автоматически обнуляться. Выполнение терминально завершается отдельно от полномочий на публикацию.

### 2. Переходы и восстановление

- Перед любым внешним write фиксировать durable intent с точным scope и уникальным effect ID.
- После restart сначала **сверять фактические процесс/Git/GitHub evidence**; не запускать новую попытку из-за отсутствия ответа.
- Подтверждённый старый Review не имеет права автоматически испортить актуальное Review; но любой текущий UNKNOWN/AMBIGUOUS ownership удерживает безопасность.
- После законченного Coding/Review публикация получает отдельное ограниченное разрешение согласно политике; истечение execution permit не должно стирать Chief/Owner решения и проверенный tree.
- Запрещено удалять holds/claims ради устранения симптомов. Recovery должен иметь явный контракт на конкретную неопределённость и оставлять аудит.
- При превышении correction limit -> `NEEDS_OWNER`, а не бесконечный цикл.

### 3. Наблюдаемость

У каждой Issue короткий ответ: `этап / текущий attempt / тесты / blocker / next action / ссылка PR`. Подробный журнал отдельно.

## Открытые вопросы на согласование

1. Должна ли система создавать Draft PR после PASS Review автоматически без Chief для PERSONAL (рекомендация: **да**), а Chief вызывать как необязательный post-PR gate?
2. Сколько correction attempts разрешено для PERSONAL? (предложение: 2.)
3. Что делать с зависшим `UNCERTAIN` внешним эффектом: блокировать только одну Issue/репозиторий или весь управляющий сервис? (рекомендация: минимальный безопасный scope.)
4. Сколько времени хранить полные логи, кодовые снимки и доказательства?
